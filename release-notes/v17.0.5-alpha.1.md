# Musoq 17.0.5-alpha.1 - Runtime Binding and Aggregate Correctness

This full-train alpha hardens runtime-v2 source binding, generated C# CLR reference discovery, and distinct aggregate execution across relational and execution-target transitions.

This release publishes:

- `Musoq.Parser`
- `Musoq.Plugins`
- `Musoq.Schema`
- `Musoq.Evaluator`
- `Musoq.Converter`

## Highlights

- Preserved schema ownership and provider-method binding across materialized row carriers, CTEs, set operations, joins, nullable outer-join projections, and downstream relational transitions.
- Required explicit aliases for source-injected provider methods when multiple source aliases are eligible, preventing an otherwise shared implementation from receiving the wrong source row or nullability context. The language specification now documents this MQ3035 rule.
- Added behavior and implementation-path coverage for `COUNT(DISTINCT)`, including overloads, grouped and ungrouped queries, compositions, empty aggregates, streaming, parallel execution, and generated query inspection.
- Added demand-driven CLR reference discovery for generated C# execution. Execution-plan requirements now identify external assemblies and nested CLR property types without broad application-domain reference loading.
- Added deterministic missing-reference diagnostics, external CLR end-to-end fixtures, architecture guardrails, generated-code samples, and focused reference-discovery benchmarks.

## Compatibility

- A source-injected provider method that is available through multiple aliases must now be qualified with its source alias; otherwise the query reports MQ3035 (`AmbiguousMethodOwner`). Alias-independent utility methods retain common-method auto-resolution.
- Generated C# execution now fails closed with a target diagnostic when a required CLR reference cannot be resolved or is not a valid metadata image.
- No standalone target packages are introduced. The target implementations remain bundled through `Musoq.Converter`.

## Manual impact

This is a core runtime and language release. The commits do not change CLI commands, service behavior, supported tool endpoints, installer behavior, or the Cloud-owned CLI manual. The development manual freshness audit is therefore run in check-only mode.
